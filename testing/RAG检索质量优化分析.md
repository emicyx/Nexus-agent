# RAG 检索质量（召回率/精准率/相关性）低的原因与优化分析

> 分析日期：2026-08-02
> 依据：28 条黄金用例 × 三条检索路径（纯向量 / 纯关键词 / RRF 融合）逐问题对比实验
> 实验脚本：`testing/eval_rag/optimize_analysis.py`（三路排名）、`diagnose_retrieval.py`（余弦距离）
> 基线（修复 rag_search 工具语法 bug 后）：Recall@5=0.464 / Precision@5=0.107 / MRR@10=0.342 / NDCG@10=0.427 / top1 黄金命中=0.25

---

## 一、结论速览

**召回率/精准率/相关性低的根因，按影响排序：**

| # | 根因 | 证据 | 影响 |
|---|---|---|---|
| 1 | **检索实际只有向量一路，关键词路形同虚设** | 纯关键词 top-5 命中仅 1/28；RRF 融合 = 纯向量 | 失去"第二路救命"能力 |
| 2 | **向量排序质量是硬瓶颈** | 相关块余弦相似度仅 0.52~0.67；黄金分块 50% 在 top-5、29% 在 top-10 外 | 召回/精准/相关性全部受限 |
| 3 | **切块质量伤害匹配** | 失败用例的黄金分块多为 500 字硬切碎片或密集表格 | 语义被稀释/截断 |
| 4 | **精准率低的构成因素** | 280+ 分块仅 1~2 个黄金；向量把"相近但错误"块排在前面 | Precision 结构性偏低 |
| 5 | **放大器：Agent top_k=5 + 预注入阈值 0.65 过严** | R@10=0.71 而 R@5=0.50；相关块相似度 <0.65 被预注入挡在门外 | 生成层拿不到证据 |

---

## 二、根因分析

### 2.1 关键词路形同虚设 → 混合检索退化为纯向量（最大结构性问题）

**三路路径逐问题对比**（黄金分块命中数 / 28 条）：

```
纯向量    top5=14/28 (0.50)   top10=20/28 (0.71)
纯关键词  top5= 1/28 (0.04)              ← 几乎不工作
RRF融合   top5=14/28 (0.50)   top10=20/28 (0.71)   ← = 纯向量
```

**根因**：`search_documents` 关键词路用 `plainto_tsquery('chinese', q)`。zhparser 会把自然问题切成 5~8 个 token 并**全部 AND**：

```sql
-- 查询 "Nexus 平台的数据库技术选型是什么"
plainto_tsquery('chinese', ...) = 'nexus' & '平台' & '数据库' & '技术' & '选型' & '是'
```

要求某个分块同时包含全部 token（含"平台/技术/是"这类泛词），几乎不可能命中 → **28 条仅 1 条关键词路命中**。RRF 融合（k=60）在关键词路无输出的情况下，退化为纯向量排序，第二路完全没起到兜底作用。

### 2.2 向量排序质量是硬瓶颈（相关性低的直接原因）

对每个查询的黄金分块测余弦距离（`diagnose_retrieval.py`）：

- 相关块的余弦距离普遍 **0.33~0.48**（相似度 0.52~0.67），少数优秀用例 0.14~0.30；
- 黄金分块在纯向量检索中的位次分布：
  - top-5：14/28（50%）
  - 6~10 名：6/28（21%）
  - **10 名以外：8/28（29%）—— 完全召回失败**（q03/q19/q24/q25/q26/q17/q23 等）

相关性指标（MRR=0.34、top1 命中=0.25）低，本质是"首条命中率"低：向量路把"语义相近但错误"的分块排在黄金分块之前。

### 2.3 切块质量伤害匹配（针对失败用例）

失败用例的黄金分块特征高度集中：

- **密集 markdown 表格**（q01/q02/q03/q10 技术栈表、q14 工具表、q18 方案对比表、q22 检查点表）：管道符 + 短单元格，语义被大量并列词稀释。例：q03"项目用哪个版本的 CrewAI"的黄金分块（技术栈表，含 Next.js/FastAPI/CrewAI/DashScope/PostgreSQL/Redis 等一堆并列技术）纯向量只排到 **36 名**；
- **500 字硬切碎片**（q15/q19/q24/q25/q26/q28，`_split_chunks` 对 >500 字段落拦腰截断）：片段从句子中间开始/结束，语义不完整；
- **抽象改写提问**（q24"agent_id 改为可空" vs 原文"`agent_id` 改 nullable"；q26"HITL 实现思路" vs 原文"宏观解决思路"）：查询与原文词面重叠低。

### 2.4 精准率低的构成因素

- 每个查询只有 1~2 个黄金分块，而库里有 280+（评估期实际 432）个分块 → Precision@5=0.107 在**分母上结构性偏低**；
- 向量路把多个"相似但非答案"分块排在前面（如 q01 返回了系统概览、核心目标等相邻章节），进一步拉低 Precision。

### 2.5 放大器：Agent 侧拿不到证据

- **Agent 检索 top_k=5**：黄金分块 29% 在 5 名以外 → Agent 根本看不到证据，只能诚实答"未提及"（忠实度高但完整性=0）。
  - 实测 Recall@10 = 0.71 ≫ Recall@5 = 0.50，**仅调大 top_k 即可显著改善**；
  - 附带发现：`config_json` 里配 `top_k` 的**参数化实际不生效**——`RagSearchTool.args_schema` 的 `top_k` 默认值是 5，LLM 不显式传参时 Pydantic 填 5，`_run` 直接使用，`top_k_default`（来自 config_json）只在解析失败时才兜底；
- **KB 预注入阈值 0.65 过严**：相关块相似度多落在 0.52~0.67，多数 <0.65 → 预注入几乎不触发（命中预注入/检索的用例完整性=1.0，未命中=0）。

## 三、优化方案（按性价比排序）

### P0 —— 低成本、立即生效、已用数据验证

**1. 将 Agent 检索 top_k 从 5 提到 10（顺带修复 top_k 参数化失效）**
- 实测召回曲线（黄金分块出现在 top-k 的概率）：top5=50% → top10=71% → top15=79% → top20=82%。
- top_k=10 时 Recall 提高约 21 个百分点，生成完整性随证据可见率同步上升；
- 修改：`RagSearchTool._run` 在 `top_k==5`（schema 默认）时改用 `self.top_k_default`（类似 tool-guide 示例的 `if top_k == 20` 逻辑），让 config_json 真正可调。

**2. 下调 KB 预注入阈值 0.65 → 0.50（或预注入候选改为混合检索 top-4）**
- 相关块相似度多位于 0.52~0.67，0.65 阈值把大部分挡在门外；
- 命中预注入的用例完整性=1.0，此改动直接提升生成完整性。

### P1 —— 中成本、已验证有效

**3. 修复关键词路：查询取 top-N 关键词做 OR（去掉"是/什么/的"等泛词）**
- 现状 `plainto_tsquery` AND 全部 token 导致 28 条仅 1 条命中；
- 改为：对查询分词后取前 2~4 个信息量最大的词做 `to_tsquery('chinese', 'k1 | k2 | k3')`，或改用 `websearch_to_tsquery`；
- **已实测**：OR 方式可救回 q01/q03/q10/q17/q26 等 5+ 条原本 top-10 完全失败的用例（如 q26 `HITL|人类审批|实现思路` 命中黄金分块 pos1）。关键词路恢复后，RRF 融合才有真正的"双路"价值；
- 局限：纯语义改写（如 q24"可空" vs "nullable"）关键词路救不回，需配合重排/查询改写。

**4. 标题/表格感知切块**
- 按 markdown 标题（`#`/`##`/`###`）优先分段，避免把章节拦腰截断；
- 表格按"表头 + 行"切块而非整表硬切；
- 段落间保留 50~100 字重叠；长度上限从 500 放宽到 800~1000；
- 直接改善 q01/q03/q10/q14/q18/q22（表格）与 q15/q19/q25/q26（硬切碎片）这类用例。

### P2 —— 高成本、效果最强

**5. 两阶段重排（Rerank）**
- 向量检索取 top-20~50 → 用 cross-encoder（如 bge-reranker-v2）或 qwen LLM 轻量重排 → 取 top-5；
- 对"黄金分块在 6~39 名"的硬用例最有效（q03/q24/q25/q26 等）。

**6. 查询改写 / 多路召回**
- LLM 把用户问题改写为 2~3 个子查询（multi-query），或生成假设答案再检索（HyDE），合并去重；
- 直接缓解"抽象改写提问"（q24 类）。

**7. 更强/带指令的 embedding**
- 对比 bge-large-zh / text-embedding-v4；或对查询加指令前缀（如"这是关于项目 Nexus 的一个问题"）；
- 当前 text-embedding-v3 对中文技术文档相关块相似度仅 0.52~0.67，区分度有限。

### 基建
- **正式应用 Alembic 迁移 / 补 ivfflat 索引**：当前 `document_chunks` 无向量索引（精确扫描，432 块下正确性无损），数据量上万后必须补建并设 `ivfflat.probes`。

## 四、预期收益（估计）

| 方案 | 对 Recall@5 / 完整性的预期 |
|---|---|
| P0-1 top_k 5→10 | 证据可见率 50%→71%，完整性随命中率同步提升 |
| P0-2 预注入阈值下调 | 命中预注入用例完整性=1.0，覆盖面扩大 |
| P1-3 关键词路 OR 修复 | 救回 5+ 条 top-10 失败用例，Recall@10 约 0.65→0.75+ |
| P1-4 切块优化 | 表格/碎片类用例匹配显著改善 |
| P2-5 重排 | 对硬用例 Recall@5 可能达 0.8+（行业常见提升） |

> 建议实施顺序：P0-1 → P0-2 → P1-3（三者改动小、见效快）→ P1-4 → P2，每步后用本测试集复测对比。
