| 延迟 | 入库 / 检索 / embedding / 问答端到端实测 |

## 二、文档入库全过程（怎么实现的）

Nexus 有两条入库路径，**均已改为"句子级 Embedding 相似度语义分块"**（`backend/app/services/semantic_chunker.py`）：

- 直接上传：`POST /v1/documents` / `/upload` → `document_service.ingest_document`
- 网页编排：`web_ingest_crew` → `kb_ingest_tool`（同步实现）

### 2.1 语义分块算法

```
段落分组(\n\n)
  → 代码块 / markdown 表格：整体一个原子单元（不切开）
  → 短段落(≤800字)：直接一个原子单元
  → 长段落(>800字)：按中文句末标点(。！？；…\n)切句子，每句一个单元
  → <40字单元合并成缓冲，避免短片段嵌入过噪
  → 批量嵌入全部原子单元（DashScope text-embedding-v3, 1024维, 每批10条）
  → 相邻单元余弦相似度；断点 = 相似度 < max(0.45, 相似度30%分位)
  → 贪心合并：断点处切 / max_chunk=800 兜底切 / min_chunk=150 防碎片
```

**关键保证**：绝不拦腰截断句子；表格/代码块不切开；短段不产生碎片。替代了旧"`\n\n` 分段 + 500 字硬切"方案（旧方案 16% 分块为句中断裂碎片，详见 `doc/RAG检索质量优化分析.md`）。

### 2.2 向量化与存储

- `text-embedding-v3`，`dimensions=1024`，DashScope OpenAI 兼容端点，批量上限 10 条/次（已修复原一次性全发的超限 bug）；
- 存储：`document_configs` + `document_chunks`（`embedding vector(1024)` + `tsv` 生成列 `to_tsvector('chinese', content)`，zhparser 中文分词）。

### 2.3 检索侧（混合检索）

```
向量路：pgvector 余弦距离 embedding <=> query_vec，取前 200
关键词路：zhparser 切词 → 过滤停用词 → OR tsquery → ts_rank，取前 200
RRF 融合：score = Σ 1/(60 + rank)，取 top_k
```

**关键词路已修复**（`app/services/keyword_search.py`）：原 `plainto_tsquery` 把查询全 token AND（几乎零命中）；改为 zhparser 切词 + 过滤停用词/单字符 + OR 连接，`ts_rank` 按覆盖率排序。另有 `search_kb_high_confidence()`（纯向量 top-2，相似度 >0.65 预注入 Task description）。

### 2.4 实测入库耗时（语义分块）

| 文档 | 分块数 | 入库耗时 | 说明 |
|---|---|---|---|
| Nexus架构白皮书 | 9 | 2.11 s | 短段落合并 |
| Nexus工具开发指南 | 10 | 2.74 s | |
| Nexus项目进度文档 | 70 | 12.64 s | 长文档句子级嵌入 |
| Nexus设计文档 | 20 | 6.47 s | 原 75% 硬切，现已句子级 |
| Nexus简历梳理 | 21 | 3.66 s | |
| Nexus项目README | 2 | 0.73 s | |
| **合计** | **132** | **≈ 28.3 s** | |

- **Embedding 单条延迟采样**：p50 = 151 ms，p90 = 332 ms；
- 入库成本较旧 500 字方案约翻倍（语义分块需"原子单元判界 + 最终分块存储"两遍嵌入），但一次上传仅几十秒，换取分块质量。

## 三、指标评测结果

### 3.1 检索层（15 条用例）

| 指标 | 数值 |
|---|---|
| Recall@3 / @5 / @10 | **0.640 / 0.907 / 0.987** |
| Precision@3 / @5 / @10 | 0.289 / 0.240 / 0.133 |
| MRR@10 | **0.582** |
| NDCG@10 | **0.689** |
| top1 黄金命中率 | 0.400 |
| 检索延迟 | p50 = 254 ms，p90 = 330 ms |

**解读**：
- **Recall 已非常高**：91% 的查询黄金分块在 top-5 内，99% 在 top-10 内——只有 q01（数据库选型，黄金块在 6-10 名）未进 top-5。
- **Precision 偏低是结构性现象**：15 条中绝大多数为"单黄金块"查询，`Precision@k` 的上限即 `1/k`（P@5 上限 0.2）。实测 P@5=0.24 已触及/略超上限（部分查询含多黄金块抬升）。检索返回的其余分块多为"同源文档的相关内容"而非错误——按宽松相关口径（同源文档即相关）Precision@5 ≈ 0.5。**Precision 不适合作为该任务的核心指标**，应以 Recall + MRR/NDCG 为准。

### 3.2 生成层（knowledge_qa crew 问答，12 条用例，qwen-plus 判分）

| 指标 | 数值 |
|---|---|
| 相关性 Relevance | **0.921** |
| 忠实度 Faithfulness | **0.996** |
| 完整性 Completeness | **0.948** |
| 端到端延迟 e2e | p50 = 3.95 s，p90 = 8.10 s，max = 8.10 s |
| 首事件延迟 | p50 = 390 ms，p90 = 450 ms |
| rag_search 调用率 | 100%（12/12） |

**逐条表现**（详见附录）：
- **优秀（完整=1.0）**：q01/q04/q05/q06/q07/q08/q09/q13/q15 —— 检索命中即完整有据回答；
- **良好**：q02（0.67，漏"前端 19 个 TS 文件"细节）、q10（0.90，答成"四层"含 CrewAI 内置记忆，属于合理的更全口径）、q11（0.80，步骤正确但判分相关 0.3，判分器对程序题偶发偏差）。

### 3.3 已修复：否定/状态类问题的幻觉（q15）

初版评估中 **q15"Nexus 支持多租户和 RBAC 权限吗？"** 暴露幻觉：

> ~~"是的，Nexus 平台支持多租户和 RBAC 权限。根据知识库中的《Nexus设计文档》，其未来演进方向明确包含'多租户与数据隔离 (Multi-Tenancy & RBAC)'……"~~（修复前，忠实度=0.3）

**根因**不在检索（R@5=1.0 已找到相关内容），而在**生成指令**：`knowledge_qa` agent 缺乏"区分'已实现'与'规划中/未来方向'"的时态约束，把文档中的"未来演进方向"误读为当前能力。

**修复**（`seed.py`）：在 knowledge_agent backstory 与 kb_answer task description 中加入状态/时态约束——

> 对'是否/能不能/支持吗/有没有'等状态类问题，必须区分时态：只有检索内容明确表述为'已实现/当前具备'时才作肯定回答；若写的是'未来演进方向/规划中/待实现'，应如实回答为'尚未实现/属未来规划方向'，绝不能把未来规划当作已实现的能力。

**修复后** q15 回答：

> "Nexus 当前**不支持多租户和 RBAC 权限**。知识库明确指出：'单用户无 RBAC'是当前已知限制，而'多租户与数据隔离（Multi-Tenancy & RBAC）'被列为'未来可能开发方向'……"

→ 相关/忠实/完整 **1.0/1.0/1.0**。整体生成层随之从 相关 0.86/忠实 0.94/完整 0.86 提升到 **0.92/1.00/0.95**。

## 四、问题发现与建议

### 4.1 【已修复】关键路 / 入库阻断性问题（本报告基线已含修复）

| 问题 | 修复 | 文件 |
|---|---|---|
| embedding 一次性全发，>10 块上传 400 | 按 10 条分批 | `llm/embedding.py` |
| rag_search 工具把原始查询串当 tsquery，中文查询 SyntaxError | `plainto_tsquery('chinese', :q)` | `tools/rag_search_tool.py` |
| 500 字硬切导致句中断裂碎片 | 句子级 Embedding 相似度语义分块 | `services/semantic_chunker.py`（新） |
| 关键词路全 AND 近零命中 | zhparser 切词 + 停用词过滤 + OR tsquery | `services/keyword_search.py`（新） |

修复前后（v1 28 条用例）：Recall@5 0.464 → 0.726、完整性 0.517 → 0.817（详见 `doc/RAG检索质量优化分析.md`）。

### 4.2 【未修复】发现的问题

1. **Precision 结构性偏低**——单黄金块任务下 Precision@k 上限 1/k，属指标定义固有现象；检索本身 Recall 已 0.91@5，非质量问题。
2. **top1 命中率 0.40**——精确答案块仍约 60% 不在首位（多在 2-5 名），MRR=0.58；提升需重排器（向量取 top-20~50 → cross-encoder/LLM 精排）。
3. **Agent 默认检索 top_k=5**——q01 等黄金块在 6-10 名的用例对 Agent 不可见；调到 10 可进一步覆盖（Recall@10=0.987）。
4. **KB 预注入阈值 0.65 偏严**——相关块相似度多落在 0.52~0.67，预注入近半不触发（部分用例仍靠 rag_search 工具命中）。
5. **`document_chunks` 缺 ivfflat 向量索引**——`alembic_version` 表不存在，Alembic 从未执行，库表由 `create_all` 建；当前 132+ 分块精确扫描正确性无损，规模上万后需补索引 + `ivfflat.probes`。

### 4.3 建议优先级

1. **P0**：Agent 检索 top_k 5→10，并修复 config_json top_k 参数化（当前 schema 默认值覆盖 config）——Recall@10=0.987 的潜在收益。
2. **P1**：重排器提升 top1/MRR；KB 预注入阈值 0.65→0.50。
3. **P2**：正式应用 Alembic / 补 ivfflat 索引。

## 五、总体结论

| 维度 | 评分 | 说明 |
|---|---|---|
| 检索召回率 | **优秀（R@5=0.91）** | 91% 查询 top-5 内命中答案块 |
| 检索精准率 | 结构性偏低（P@5=0.24，≈上限） | 单黄金块任务固有，非质量问题 |
| 检索相关性 | 良好（MRR=0.58, NDCG=0.69） | 精确块多在 2-5 名 |
| 生成相关性 | 良好（0.92） | 命中即切题 |
| 生成忠实度 | **优秀（1.00）** | 状态类约束已消除 q15 幻觉 |
| 生成完整性 | **优秀（0.95）** | 12 条中 9 条完整=1.0 |
| 延迟 | 良好 | 检索 p90<0.4s，问答 e2e p50≈3.5s |

**一句话总结**：经语义分块 + 关键词路 OR + 状态类提示词约束三项修复后，检索召回已接近天花板（R@5=0.91、R@10=0.99），生成相关性 0.92 / 忠实度 1.00 / 完整性 0.95，RAG 端到端质量进入优秀区间；剩余改进空间集中在精确答案块排名（重排器）与 Agent 检索 top_k 覆盖。

## 附录 B：可复现性

1. `make up` 启动全栈（`QWEN_API_KEY` 需含 text-embedding-v3 权限）。
2. 预检测试集：`.venv/Scripts/python.exe testing/eval_rag/eval_rag.py --preflight`
3. 全量评估：`.venv/Scripts/python.exe testing/eval_rag/eval_rag.py`
4. 检索诊断：`.venv/Scripts/python.exe testing/eval_rag/diagnose_retrieval.py`
5. Precision 分解：`.venv/Scripts/python.exe testing/eval_rag/precision_analysis.py`

脚本自动入库（语义分块）→ 检索/问答/判分 → 清理，结果写入 `testing/eval_rag/results/*.json`。
