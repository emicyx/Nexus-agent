# Nexus v2 开发纪律与运维实录

> v2 重构最有 interview 价值的部分之一：以使用证据驱动功能取舍的工程纪律，以及真实运维中攒下的踩坑记录。更新至 2026-09-17。

## 一、防玩具三纪律（反"演示项目化"）

1. **细条优先**：每条功能端到端当周可交付，以"用户手机/本机上的真实结果"收尾，禁止先铺基础设施层。
2. **复杂度按需解锁**：每建一个推迟组件，须在解锁登记表补触发证据，没有证据不建（例：LLM 路由器的触发条件 = ≥4 个 crew 日常在用或命令记忆成为负担；IM 审批卡片的触发条件 = 第一个需要在 IM 里审批的真实场景）。
3. **替代品检验**：每条功能要能一句话答出"比现成方案强在哪"——巡检 = 告警带 agent 初诊与处置建议；日报 = 私有 KB 增量；IM 问答 = 私有知识库 + 记忆随身。

## 二、7 天自用验证（唯一验收标准）

- 每条功能上线后连续 7 天真实使用才算交付；连续 7 天没用 = 砍掉或重做。
- 具体门槛示例：QQ 问答要求一周 ≥10 次真实提问；定时任务要求日报连续 7 天到达 + down→up 告警演练 + 断连演练（停协议端一晚，验证落账与重连续推）。
- 技术指标（单测/集成/评测/CI）只是入场券，不等于交付。

## 三、砍功能决策实录（按证据取舍，不是做不动）

- **team_orchestrator 退役（R0）**：crew 内 LLM manager 即兴编排慢、贵、不可测；职责被确定性入口路由（route_v0）与专职 crew 取代。
- **钉钉双向接入 → 定向变更为告警备推 → 搁置（三步，2026-09-16/17）**：
  1. 原始动机"监听公司钉钉群公告"经核实**不可行**——用户非企业管理员，自建企业的机器人进不了公司组织的群（钉钉企业间完全隔离）；群自定义机器人只能发不能收；公告不 @ 机器人永远到不了机器人；钉钉无个人消息 API，也不接受在公司 IM 上跑非官方客户端（纪律/安全风险）。
  2. "自建企业里自用问答"无真实场景——7 天 ≥10 次提问必不过，防玩具纪律直接砍；保留价值收敛为"QQ 被风控时的告警兜底通道"（背景：2026-09-16 NapCat 失联约 5 小时的教训），做成 webhook 加签备推（backup/always/off 三态）。
  3. 代码完成并部署当天，用户裁定"做了也没意义，暂时搁置"——不建机器人、不做验收演练；代码休眠（凭据未配置 = 零行为差异），启用成本约 2 分钟。
- **飞书双向接入不开工（2026-09-17）**：开工门问题"会真的每天在飞书里跟它说话吗"——用户如实回答不会（学生身份，项目定位为经验积累 + 简历 + 实用工具，无飞书日常场景）。前置的 im_pipeline 渠道无关抽象（阶段 A）作为纯重构已独立交付——架构价值（渠道无关管线 + 注册表 + 抽象守卫测试）不依赖第二个渠道真接入。
- **方法论总结**：先问"真实使用场景是否存在"再动手；没有场景的功能做完也是负资产（维护成本 + 认知负担）。砍掉的方案不做删除处理，存档解锁条件（钉钉解锁 = QQ 再发真实失联事件；飞书解锁 = 日常主用 IM 变为飞书）。

## 四、运维踩坑实录（运行账本精华）

- **Docker Desktop 崩溃**：会硬杀全部容器（postgres/redis/backend/frontend 无 restart policy 全停），且可能打掉 NapCat 的 NTQQ 登录态。恢复链 = 启动 Docker Desktop → 重建拉起容器栈 → NapCat WebUI（localhost:6099，仅 loopback）重扫码。
- **QQ 风控（错误码 168"账号存在安全风险"）**：连续重试扫码会触发；正确姿势是先在手机 QQ 上完成安全验证再扫（2026-09-16 实录：从崩溃到恢复约 5 小时）。
- **改 .env 后必须重建容器**：`restart` 不会重读 env_file（实测坑）——配置变更要走 up -d 重建。
- **SEED_DEMO_DATA=false 的坑**：启动会跳过 seed 同步（crew/agent/工具配置不更新），需在容器里手动跑一次 ensure_seed()（历史事故教训）。
- **本机库正式采纳 alembic 迁移链（2026-09-17）**：此前 schema 一直走 create_all、无 alembic_version 表；采纳时对存量库 stamp 到 0010 再 upgrade 0011。全新环境仍由 create_all 建全量 schema，无需手动迁移。
- **宿主机夜间停机 = 调度点丢失**：8:00 日报在整机不在运行时不会补发，重启后 next_run 正确顺延（如实记录，非调度故障）；云端迁移后此边界解除。
- **告警稀疏纪律**：state_change 策略天然节制；消息超长自动分段（单条 <1500 字）+ 温和频控。

## 五、评测与质量门禁

- 三套评测 + jobs 适配用例：capability（多智能体能力事故集）、rag（检索问答）、redteam（注入/越权/破坏尝试）、jobs（定时任务零外发）。
- scorer 8 种硬评分器 + LLM rubric；主指标 TSR（任务完成率，完全/部分/错误/未完成四级）。
- **judge_error 纪律**：任一硬评分器故障即该试验不可判（不允许静默通过）——防"评分器坏了 = 用例假绿"。
- **成本分层**：日常缺省 core 层（防回归锚 + 安全不变量，约为 full 层一半 token），里程碑验收显式跑 full；修复验证用 --trials 3 定点。
- 数据集版本化（当前 v2026.09.14）；每次变更全量回归（单测 + 集成 + 评测 core 层）+ CI 三 job 全绿才算交付。
- 评测的封闭环境控制：走真实 HTTP 栈、SSE 流式、自动审批、沙箱清理、按用例临时入库语料并在用例后回收；零外发硬断言（见《Nexus v2 定时任务与推送》）。
