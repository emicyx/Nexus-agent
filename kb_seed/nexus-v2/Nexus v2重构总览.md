# Nexus v2 重构总览（2026-09）

> 定位：v2 把 v1 的"Web 端多智能体聊天平台"改造成**常驻个人助理**——定时/事件触发任务、连接 IM 渠道收发消息、产物推到用户手机。
> 更新至 2026-09-17。本文只写 v2 增量；v1 基础架构（三层记忆、SSE 事件流、混合检索、HITL 审批等）见《Nexus架构白皮书》《Nexus设计文档》等既有文档。

## 一、为什么重构（v1 的自用结论）

- v1 形态的问题：对话由前端发起、产物困在沙箱，用户不打开电脑就没有服务。真实使用统计结论：**只有知识库问答被持续使用**。
- v2 目标形态：助理常驻后台——到点自动做事（巡检、日报）、状态变化主动找人（告警）、用户在 IM 里随时提问（私有知识库 + 记忆随身）。
- 唯一验收标准是**7 天自用保留**：每条功能上线后，用户连续 7 天真实使用才算交付；连续 7 天没用 = 砍掉或重做。技术指标（测试通过、部署成功）只是入场券。

## 三、当前运行形态（2026-09-17）

- 本机 Docker Compose **五容器**：postgres（pgvector + zhparser）、redis、backend、frontend、napcat（QQ 协议端）。
- 三个默认定时任务：每 30 分钟巡检（只在状态变化时推送）、每日 8:00 巡检日报、每日 21:00 KB 增量日报。
- 质量基线：单元测试 396 项、集成测试 62 项全绿；评测 core 层 TSR 100%；CI 三 job（前端类型检查+构建 / 后端单测 / 后端集成）全绿。
- 数据库迁移走 alembic 链（head=0011），全新环境由 create_all 建全量 schema。

## 四、核心设计原则

1. **复用执行引擎，不另造执行器**：IM 入站问答与定时任务都走与 Web 端相同的 crew 装配执行链路（每请求从 DB 装配、用后即毁，配置热更新天然成立），三层记忆与成本采集全生效。
2. **全系统唯一出口**：所有 QQ 发送（对话回复与主动推送）都经同一个出口函数；推送目标只来自环境变量，模型不可填。
3. **单实例铁律**：同一 QQ 账号只能跑一个 NapCat（双实例 = 互踢 + 高封号风险）；开发期本机独占，云端迁移时先停本机再启用云端。
4. **单租户边界保持**：多租户与 RBAC 当前不支持（无第二用户，属伪需求），为明确的未来演进方向。
5. **防玩具纪律**：复杂度按需解锁——每个推迟组件登记触发条件，没有真实触发证据不建（详见《Nexus v2 开发纪律与运维实录》）。
