# SOP 12 · 维护与版本迁移

> 目标：游戏更新后正确维护已发布的 mod；把存量 classic 原生 mod 迁移到 stable API。
> 前置：SOP 11（已发布）。
> 源文档：[stable-native-mods](../TeamfightManager2Mod/docs/stable-native-mods.md) ·
> [native-rust-mods](../TeamfightManager2Mod/docs/native-rust-mods.md) ·
> [native-mod-api-reference](../TeamfightManager2Mod/docs/native-mod-api-reference.md)

## 1. 游戏更新后的维护矩阵

| mod 类型 | 游戏更新后要做什么 |
|---|---|
| 数据/美术 mod（JSON、图片、文本、覆盖、立绘包） | 通常无需重编译（没有编译物）。检查 `base` 版本要求是否仍成立；重大更新后回归测试内容是否仍按预期工作 |
| Stable 原生 mod | **无需重编译**即可继续加载。但 ABI 兼容 ≠ 行为兼容：游戏机制变了，mod 的**行为**可能偏移——大更新后务必实测（见第 2 节） |
| Classic 原生 mod | 每次游戏更新都要用匹配的新 SDK **重编译**再更新 Workshop；0.6 起 classic SDK 停止分发 → 必须迁移（见第 4 节） |

### 数据 mod 的版本检查

- Early Access 期 `base` major 为 `0`；minor 变化 = 功能/内容/数据格式/兼容行为变化。
- 游戏发了兼容性变化的小版本（如英雄数据格式调整）→ 把 `base` 下限提到该版本
  （例如 `">=0.4.14"`），旧版本玩家会得到清晰诊断而不是奇怪的行为。
- 用 SOP 00 的解包功能 diff 新版基础数据，确认你的量级/键名/标签没被改。

## 2. Stable mod 更新后的回归测试

stable API 的承诺是「能加载、优雅降级」，不是「行为不变」。大更新后：

1. 重启游戏，确认无诊断、mod 未被禁用（panic 也会禁用 mod，看
   `%APPDATA%\TeamSamoyed\TeamfightManager2\data\log.log`）。
2. 跑核心场景：新英雄技能、物品回调、UI 交互、AI 钩子、自定义模式。
3. 新增的未知枚举码会以 `None` 出现——你的代码本就该跳过（SOP 08 §4）；
   若新场景需要适配，按新 SDK 增量修改。
4. 新游戏版本的新能力（reference 中标 **`0.5.4+`** 之类的条目）：
   用最新 SDK 重编即可使用；旧游戏上调用这些新 API 自动返回 `None`/`false`。
5. 需要强制最低游戏版本时（节制使用）：`declare_stable_mod!(init, requires = 2);`
   （requires=2 → 0.5.4+），玩家会得到「请更新游戏」诊断而不是哑 mod。

## 3. 版本号与发布节奏

- `mod.mod_info` 的 `version` 每次发布递增；`last_updated` 同步更新。
- 存档命名空间版本（SOP 09 §3）与包版本**相互独立**，不要混用。
- 内容 id（英雄 id、`action_name`、buff name、服务 id）发布后**保持稳定**：
  存档、补丁、ban/pick 引用它们（SOP 01 / 02）。

## 4. Classic → Stable 迁移

### 4.1 为什么必须迁

- classic SDK 仅支持到游戏 **0.5**；**0.6 起不再随游戏分发或更新**。
- classic DLL 绑定单一精确游戏构建，每次更新都要重编；Windows 专用。
- stable 路径已覆盖 classic 全部能力及更多（英雄、物品、效果、完整 UI 控制、
  渲染覆盖、音频、热键、存档、网络、管理记录与事件、转会、地图/比赛自定义、
  两个 AI 钩子面）；classic 独有而 stable 没有的已不存在
  （相反：出装钩子、护盾、攻速读取、分路先验是 stable 0.5.4 新增、classic 没有）。
- 遇到 stable 契约确实做不到的 → 上报让 stable API 增长该函数，
  **不要**为此新开 classic mod。

### 4.2 概念映射表

| classic（`mod_api`） | stable（`mod_api_stable`） |
|---|---|
| `fn init(&GameCtx) -> ModRegistration` + `declare_mod!` | `fn init(&StableHost) -> StableMod` + `declare_stable_mod!` |
| `ModRegistration::new("id")` | `StableMod::new("id")`（id 仍须等于文件夹名） |
| `reg.add_champion` / `replace_champion` | `decl.add_champion`（**复用现有 id 即改版**，无单独 replace 调用） |
| `ModChampionInfo` | `StableChampion`（新增 `lane_prior()` 等） |
| `ModAction` / `ModEffect` / `ModEffectType` | `StableAction` / `StableEffectSpec` / `StableEffectType` |
| `ModPassive` | `StablePassive`（钩子同构：`on_spawn/on_attack/on_damaged/on_kill/on_update/on_base_attack/on_assist/on_dead`） |
| `ModItemInfo` | `StableItem`（新增 `on_upgrade/on_upgraded_from/on_cc`、crit/attack_type 参数等） |
| `reg.set_extension` → `ModExtension`（`Scene/GameUI/Assets/dt`） | `decl.set_extension` → `StableExtension`（`&mut StableClient`、`dt_micros`） |
| `reg.set_server_extension` → `ModServerExtension`（`ServerModContext/Database`） | `decl.set_server_extension` → `StableServerExtension`（`&mut StableServerCtx`，JSON 文档读写） |
| `reg.add_draft_score_hook`（`ModDraftScoreHook`） | `decl.add_draft_score_hook`（`StableDraftHook`，新增 `decide_ban/decide_pick` 全量覆盖） |
| `reg.add_player_input_ai`（`ModPlayerInputAi`） | `decl.add_player_input_ai`（`StablePlayerAi`，`ctx.sim()` 可读全模拟） |
| —（classic 无） | `add_native_effect`、`add_item_build_hook`、`set_map_customizer`、`set_match_hook`、服务注册同 `host.register_service` |
| `GameCtx` 模拟调用（`deal_damage/heal/add_buff/apply_cc/...`） | `StableSim` 同名/近名调用（新增护盾、直接变更、生成、策略文档等） |
| `ClientData`（`Scene::InGame { data }`）+ `mod_save_*(MOD_ID, k)` | `StableClient`（InGame）+ `save_*(k)`（自动命名空间，SOP 09 对照表） |
| `ctx.database.mod_save_data`（服务器直写） | `ctx.save_set_*`（服务器上下文） |
| 直接借用游戏内部类型（`Team`、`Athlete`、`ChampionInfoSheet`…） | 契约化值类型（`StatV1`、`BuffV1`、`ChampionBriefV1`…）+ JSON 文档路径读写 |
| `API_VERSION (0, 8)` 符号 / 每版重编 | 无版本符号负担；`requires = N` 可选最低版本 |
| 仅 Windows（x86_64 MSVC） | Win / macOS / Linux，每平台自构建 |

### 4.3 迁移步骤

1. 按 SOP 08 §2 用 `mod-sdk-stable/template/` 建新工程（或就地改造）：
   依赖换 `mod-api-stable`（path 指向 SDK；上传器构建时自动注入）。
2. 入口改为 `init(&StableHost) -> StableMod` + `declare_stable_mod!`。
3. 按上表逐项搬注册调用；内容逻辑大体同构，类型与上下文按
   [Stable API Reference](../TeamfightManager2Mod/docs/stable-api-reference.md) 替换。
4. 直接访问内部游戏类型的地方改为：值类型（`StatV1`/`BuffV1`）或
   JSON 文档路径（`record_get/set_json`、`setting_get/set_*`）。
5. 模拟回调内补齐确定性纪律（`rng_seed` 派生随机、去 `unwrap`）。
6. 本地完整回归（SOP 10 分层清单），特别是存档兼容：命名空间版本沿用旧值，
   保证老玩家存档数据无缝续读（SOP 09 §3）。
7. 原 Workshop 物品就地更新（SOP 11 §3）：同文件夹、同 id、版本递增、change note
   写明迁移到 stable（此后不再需要每次游戏更新重编）。
8. 多人注意事项同步更新：stable 支持三平台，若你补齐 `.so`/`.dylib`，
   `Runs on:` 行会自动扩展。

### 4.4 classic 维护期的临时守则（尚未迁移时）

- SDK 与游戏版本严格匹配；SDK 变化的更新后重编并更新 Workshop。
- DLL 文件名与 mod 文件夹名一致；注册 id 同样。
- 上传时源码路径（`src/`、`target/`、`Cargo.toml`、`Cargo.lock`）自动被跳过。
- 诊断报「API 版本符号缺失/不匹配」= 旧 SDK 构建 → 用当前 SDK 重编。

## 5. 维护检查单（每次游戏更新后过一遍）

- [ ] 阅读更新说明，判断是否涉及英雄数据格式 / mod 接口 / 兼容行为
- [ ] 数据 mod：解包新版 `base_unpacked`，diff 相关资产
- [ ] stable 原生 mod：无诊断加载 + 核心行为回归（本 SOP §2）
- [ ] classic 原生 mod：取新 SDK 重编（或启动迁移）
- [ ] `base` 依赖下限是否需要上调
- [ ] 版本号、`last_updated`、change note 更新后发布
- [ ] 订阅者反馈的诊断弹窗截图按 [SOP 10](10-测试与故障排查.md) 对号入座
