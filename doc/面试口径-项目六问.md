## 一、pgvector vs ChromaDB：统一为「只用 pgvector，Chroma 是被我关掉的传递依赖」

**不要用**「原型 Chroma → 正式迁 pgvector」或「知识库 Chroma + 偏好 pgvector」的话术——git 全历史不存在任何 Chroma 使用/迁移痕迹，一追问迁移成本就穿帮。

**统一口径：**
> 「向量存储只用了 pgvector。ChromaDB 是 CrewAI 内置记忆（STM/Entity Memory）的传递依赖，我在配置层用 `CREWAI_NATIVE_MEMORY_ENABLED=False` 把它关掉了，改用自建三层记忆：短期记忆用 Redis 滚动摘要、长期记忆和知识库都用 pgvector。关掉的原因有两个：一是向量数据和业务数据（document_chunks、user_memories）同在 PostgreSQL，一份运维、事务一致；二是我的检索是混合检索——向量余弦 + zhparser 中文全文检索做 RRF 融合，tsvector 和 GIN 索引本来就在 PG 里，引入独立向量库反而多一个组件、还做不了跨路融合的 SQL。」

**事实依据：**
- `backend/requirements.txt:35` 只有 pgvector，无 chromadb 直接依赖（是 crewai 1.9.3 的传递依赖）
- `backend/app/config.py:110-115` `CREWAI_NATIVE_MEMORY_ENABLED: bool = False`
- `backend/app/crews/factory.py:496` 注释明确「避免 CrewAI 任何内置记忆创建」
- `infra/postgres/Dockerfile` 基于 `pgvector/pgvector:pg16`
- `backend/app/services/hybrid_search.py:26-61` 向量 `<=>` cosine + `to_tsquery('chinese')` + RRF(k=60)
- `backend/alembic/versions/0002_documents.py:43` `Vector(1024)` 列 + ivfflat 余弦索引
- 全仓 grep 无 `import chromadb`

**追问防线：**
- 「为什么不用专门的向量库？」→ 数据量级（132 分块的评测集、生产也是中小规模知识库）下 ivfflat 完全够用，检索 p50 约 254ms；省一个组件的运维成本。
- 「embedding 什么模型？」→ DashScope text-embedding-v3，1024 维，批量 10（`backend/app/llm/embedding.py`）。

## 二、工厂模式：统一为「配置存 DB，每请求动态装配，改配置即时生效」

「脚本热更新」这个词**删掉**——仓库里没有文件监听、没有 reload 端点，说了必被追问机制。

**统一口径（一句话版）：**
> 「所有 Crew/Agent/Task/工具配置都存在 PostgreSQL 的配置表里，每次请求时 `build_crew_from_db()` 现场读库、动态装配一个 Crew，执行完即销毁。因为不做任何缓存，前端改完 Prompt/工具配置，下一次请求天然就是新配置——热更新是『无缓存』这个设计的自然结果，不需要任何缓存失效逻辑，也不用重启服务。」

**事实依据：**
- `backend/app/crews/factory.py:242` `build_crew_from_db()`，:248-251 docstring「每次调用新建 Crew，执行后即销毁，配置热更新天然成立」
- 配置表：`crew_configs/agent_configs/task_configs/skill_configs/tool_configs`（`backend/app/models/`）
- 启动时不构建不缓存（`backend/app/main.py:102-153` 只做建表/种子/LLM 预热）
- `doc/architecture.md:143` 文档同口径

**追问防线（体现深度，主动说）：**
- 唯一的缓存例外：默认 crew_id 有 5 分钟 TTL 缓存（`factory.py:926-943`），但 CRUD 时主动失效（`crew_service.py:61,85,95`）——因为「拿默认 crew」发生在每条消息入口，不想每条消息都查一次库。
- LLM 实例按 `(model, temperature)` 缓存（`factory.py:47,63-87`），改配置会产生新 key，下个请求生效。
- 边界诚实：**工具类注册表是静态 Python dict**（`tool_registry.py:20`），新增一个工具类要发版；但配置层面的增删改（prompt、挂哪些工具、温度、任务依赖）全是热生效。这个边界主动讲，比被问出来强。
- 动态输出模型：从 DB 的 JSON schema 用 `pydantic.create_model` 现场生成（`factory.py:673`）。

## 三、HITL 审批状态机：先讲清现状，再主动讲竞态和修法（测开加分位）

**统一口径：**
> 「审批单存 Redis，状态机是 PENDING → APPROVED / REJECTED / TIMEOUT / CANCELLED 五态。触发路径有两条：Agent 主动调 human_approval 工具，或者给任意工具挂通用前置审批 hook（批准才执行原工具，拒绝/超时就短路返回『工具已取消』）。超时是惰性实现的，没有定时任务：工具侧在 worker 线程里每秒轮询 Redis，150 秒 deadline 到点把状态写成 TIMEOUT；Redis 键本身 300 秒 TTL 是第二层兜底，进程即使挂了审批单也会自动消失。审批通过后不重跑任务——原工具在同一个 kickoff 的同一个线程里继续往下走，天然不重复执行。客户端断连会置 CANCELLED 并抛取消异常终止整条运行。」

**事实依据：**
- 状态枚举：`backend/app/schemas/approval.py:14`（PENDING/APPROVED/REJECTED/TIMEOUT）+ CANCELLED（`human_approval_tool.py:41`）
- Redis 键 `approval:<id>`、TTL 300：`backend/app/db/redis.py:94-108`
- 轮询 150s/1s：`backend/app/tools/human_approval_tool.py:32-33,163-197`
- 决策端点 `POST /v1/approvals/{id}`：`backend/app/api/v1/approvals.py:44-60`
- 通用 hook：`backend/app/crews/tool_hooks.py:149-234`；种子挂在 kb_ingest 和 write_markdown 上
- 测试：`testing/unit/test_approvals.py`、`testing/integration/test_api_approvals.py`、`testing/e2e/smoke_hitl.py`

**主动认领的竞态（这是测开面试的得分点，别等被问）：**
> 「现在有一个我知道的缺陷：决策接口是 Redis 的读-改-写，不是原子的，也没有校验当前必须是 PENDING。理论上迟到的 approve 能把 TIMEOUT 覆盖成 APPROVED，虽然工具侧早按超时返回了，不会真的重复执行危险操作，但状态会被污染。修法很明确：用 Lua 脚本做条件更新——只有 `status == PENDING` 才允许写 APPROVED/REJECTED，一步完成比对和写入，单命令原子；再加决策接口幂等（重复 approve 返回终态而不是再写一次）。如果要扛进程重启，就把审批单落 PG 表，Redis 只做通知通道。」

## 四、通义千问适配层：自研 HTTP 适配 + 明确的重试/降级边界

**统一口径：**
> 「我没有用 litellm 也没有用 DashScope SDK，自研了一个继承 CrewAI BaseLLM 的 AliyunLLM，直接裸调 DashScope 的 OpenAI 兼容端点，同步用 requests、异步用 httpx。原因是要拿到底层控制权：流式解析、tool_calls 跨 chunk 拼接、重试策略、错误分类，这些走中间层都会被屏蔽。
> Function Calling：工具 schema 由 CrewAI 把 BaseTool 转成 OpenAI tools 格式透传；流式返回时 tool_calls 的 name/arguments 是分片到的，我按 index 跨 chunk 累积拼接成完整调用。解析失败的策略是『净化降级』而不是重问模型：arguments 不是合法 JSON 时替换成空对象 `{}` 并打 warning——让工具自己报参数校验错误回喂给模型，比再花一轮调用去修 JSON 便宜；缺 tool_call id 才抛异常。工具执行报错也作为 role=tool 消息回喂，模型可以自行纠正参数重试，这是模型层的自愈环。
> 重试与降级：默认重试 2 次，触发条件是 5xx、429 限流、超时、网络异常；4xx（除 429）不重试直接抛，避免把坏请求重放三遍。重试耗尽后没有备用模型，走的是错误分类降级——classify_llm_error 把异常分成限流/超时/鉴权/网络等类别，附中文行动建议，以 SSE error 事件推给前端，用户看到的是『限流了，请稍后再试』而不是堆栈。另有流式失败自动回退非流式单次调用、连续 3 次空响应熔断、Token 日预算熔断、聊天接口限流+并发上限四层防护。」

**事实依据：**
- `backend/app/llm/aliyun_llm.py:163`（AliyunLLM(BaseLLM)），裸 HTTP
- schema 转换：`backend/app/crews/crewai_async_patch.py:59-61`
- 流式 tool_calls 累积：`aliyun_llm.py:1046-1197`（异步）、1274-1441（同步）
- 参数净化 `"{}"`：`aliyun_llm.py:136-160`
- 重试 2 次：`aliyun_llm.py:209-215`；触发条件 :490-511/:950-971；4xx 不重试 :513-521
- 错误分类：`backend/app/core/llm_errors.py:55-90`
- 流式回退非流式：`aliyun_llm.py:1199-1239`；空响应熔断 :439-465
- Token 预算：`backend/app/core/token_budget.py`；聊天限流：`backend/app/api/v1/chat.py:80-90`
- 单测覆盖：`testing/unit/test_aliyun_llm.py:128-225`（流式推送/跨 chunk 拼接/重试/熔断）

**追问防线（诚实短板+改进）：**
- 「指数退避怎么配的？」→ 现状是立即重试、无退避（自用低频场景够用）；上生产会改成指数退避+抖动（如 0.5s/1s/2s ±20%），并对 429 尊重 Retry-After 头。**主动说这个差距，比编一个不存在的配置强。**
- 模型矩阵：主 qwen-plus；评估器/STM 摘要/LTM 提取用 qwen-turbo 隔离小任务；多模态 qwen3-vl-plus；embedding text-embedding-v3。

## 五、指标：每个数字怎么测的，全部可溯源

### recall@5 = 0.907
> 「自建评测集：6 份真实文档、63,825 字、132 个语义分块，15 条标注了 golden 短语的 query。golden 块不是拍脑袋标的——用 golden 短语去库里实际分块文本里做子串匹配定位，保证答案块真实存在。每次检索取 top 10 再切出 @3/@5/@10，看 golden 块是否落在前 5。结果是 R@3=0.640、R@5=0.907、R@10=0.987，MRR@10=0.582。这个数字有演进轨迹：早期硬切块时 R@5 只有 0.464，改语义分块+切块上下文化后到 0.726，再做混合检索调优到 0.907——我可以讲清每一步动了什么。」

依据：`testing/eval_rag/eval_rag.py:214-258`、`test_set.json`、`results/results_20260802_125731.json`、`testing/RAG知识库量化评估报告.md:119`

### 相关/忠实/完整 = 0.86/0.94/0.86
> 「LLM-as-judge 自动评，不是人工：judge 用 qwen-plus、temperature=0、强制 JSON 输出，12 条 query 跑 chat 后打分。三个维度定义：相关性=回答是否切题；忠实度=逐句核对回答里的断言是否被 top-5 检索证据支持（防幻觉）；完整性=是否覆盖标注答案的关键点。0.86/0.94/0.86 是提示词修复前那一轮，修复后是 0.92/1.00/0.95。我也知道这个方法的局限——单 judge 模型、样本只有 12 条，报告里我自己标注了 judge 的偶发偏差（某条相关性打了 0.3），所以结论看趋势不看绝对值。」

依据：`eval_rag.py:139-165,412-422`、两份 results JSON、报告 :143,242

### 3.4s 延迟
> 「3.4s 是**端到端全量完成的 p50**（请求发起到 SSE 流读完，perf_counter 计时），p90 约 7s——不是首 token。流式下用户感知的首屏另有指标：首个 SSE 事件 p50 约 270ms，所以体感是秒回。」

⚠️ **口径警告**：3.4s（p50=3453ms）出自提示词修复**前**的 run；最终版 run 是 p50=3.95s。简历/讲述时二选一并保持一致：要么讲「修复前 3.4s」配 0.86/0.94/0.86，要么讲「最终 3.95s」配 0.92/1.00/0.95。**推荐后者**（数字全面更好），说成「端到端 p50 约 4s、首事件 p50 270ms」。
