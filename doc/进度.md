### 关键设计决策

1. **SSE 用 `StreamingResponse` 而非 `sse-starlette`**：后者对 dict 输入有双重包装 bug，直接用 StreamingResponse + `media_type="text/event-stream"` 更可控
2. **step_callback 跨线程安全**：`queue.put_nowait()` 失败时 fallback 到 `asyncio.run_coroutine_threadsafe()`
3. **最终答案分块推送 token 事件**：AliyunLLM 当前非流式 API，将最终答案按 10 字符分块 + 30ms 延迟模拟逐字输出
4. **memory=False**：CrewAI memory 默认用 OpenAI embedder，Week 1 不依赖 DB，禁用避免额外 key
5. **PG/Redis 容器先跑但不连**：docker-compose 启动容器验证健康，app 代码只放占位文件

### Week 3 关键设计决策

1. **SQLAlchemy 2.0 async + asyncpg**：原生异步 ORM，`selectin` 关系加载避免 N+1；`expire_on_commit=False` 防止异步 session 访问过期属性报错
2. **Crew 每请求新建即销毁**：`build_crew_from_db` 每次调用从 DB 重新装配 Crew，执行完丢弃 → 配置热更新无需任何缓存失效逻辑
3. **`{user_input}` 用 replace 而非 str.format**：Task description 中可能有其他 `{xxx}`，`str.format` 会报 KeyError；`replace("{user_input}", ...)` 更安全
4. **Task context 按 position 顺序构造**：维护 `task_id→Task` 映射，后构造的 Task 可引用先构造的作为 context，避免循环依赖
5. **`init_db` 用 create_all + Alembic 共存**：开发期快速建表，Alembic 作为正式迁移记录；首次用 Alembic 需 `stamp head` 对齐
6. **`single` 回退路径**：PG 未就绪时 `single=true` 走无 DB 单 Agent，保证 Week 1 闭环不破坏
7. **tool_key 注册表 + config_json 预留**：当前工具无参构造，config_json 暂只存储；为 Week 4+ 参数化工具（RAG 检索参数等）预留
8. **启动建表失败不阻塞**：`startup` 捕获异常只 warn，PG 不可用时 API 仍可启动（聊天走 single 回退）

### Week 5：HITL 人类在环拦截 + 前端配置补全

#### 5A. HITL（原计划保留）

**核心机制**：`HumanApprovalTool` + Redis 状态机

```
Agent 调用 HumanApprovalTool._run()
  → 生成 approval_id，写入 Redis: {status: PENDING, tool_input, agent_role, ts}
  → SSE 推送 approval_requested 事件
  → 轮询 Redis（每 1s），最多等 120s
  → 前端收到 SSE → 渲染审批弹窗 → POST /v1/approvals/{id} {decision: approve|reject}
  → 后端更新 Redis status
  → 工具检测到状态变更，返回 "approved" / "rejected"
  → Agent 继续或停止
```

**关键设计**：
- `HumanApprovalTool` 继承 `BaseTool`，`_run` 内用**同步 Redis 客户端**（`redis-py` 同步模式），原因同 RAG 工具——CrewAI `akickoff()` 在主事件循环中调用 `_run`，不能用 `asyncio.run`
- Redis key：`approval:{approval_id}`，TTL=300s（5 分钟兜底，前端超时 120s）
- 超时自动 reject，Agent 收到 "rejected: timeout" 后走降级路径
- 前端 `useChat` Hook 监听 `approval_requested` 事件，弹窗渲染在消息流中（而非 modal，保留上下文）

**需要做的**：
- `backend/app/tools/human_approval_tool.py`（新增）：同步 Redis 轮询 + 超时熔断
- `backend/app/db/redis.py`（重写占位）：同步 + 异步双客户端（工具用同步，API 用异步）
- `backend/app/api/v1/approvals.py`（新增）：`POST /v1/approvals/{id}` 接收前端决策

3. **Skill 种子幂等同步**：`_get_or_create_skill` 在 skill 已存在时同步 prompt_template 和 description；`_get_or_create_agent` 扩展 skills 参数，已存在 agent 时同步 skills 列表
4. **Tool 参数化用 Pydantic model field**：`RagSearchTool.top_k_default` 和 `BaiduSearchTool.max_results` 作为 Pydantic model field（非构造参数），`instantiate_tool` 通过 `cls(top_k_default=value)` 传入
5. **baidu_search top_k fallback 逻辑**：`_run` 的 `top_k` 默认值为 20，当传入 20（未指定）时替换为 `self.max_results`；用户显式传入其他值时保持不变
6. **前端 ToolForm 结构化参数表单**：按 `TOOL_PARAM_SCHEMA` 映射 tool_key→参数定义，rag_search 渲染 top_k 数字输入，baidu_search 渲染 max_results，其他工具显示"无参数化配置项"
7. **manager_agent 也注入 skills**：hierarchical 模式下 manager 的 backstory 也注入 skills prompt，与普通 agent 一致
8. **Alembic 0004 迁移**：建 `skill_configs` 表（含 name unique index）+ `agent_skills` 关联表，down_revision=`0003_hierarchical`
9. **AgentRead schema 加 skills**：`AgentRead` 增加 `skills: list[SkillRead]`，前端 `AgentCreate/Update` 增加 `skill_ids`

### Week 10：网页内容编排入库 Crew（Orchestrator 模式）

**目标**：构建"URL 抓取→markdown 撰写→主管审批循环→知识库入库"的端到端 hierarchical Crew。

**复用基建**：
- `factory.py` 的 hierarchical + manager_agent 装配机制（Week 6）完全复用，未改动
- `rag_search_tool.py` 的同步 engine + 同步 embedding 模式作为 kb_ingest_tool 模板
- `document_service._split_chunks` 切块函数被 kb_ingest_tool 直接 import 复用
- `_inject_skills` 自动将 skill prompt 注入 agent.backstory
- `wrap_tool_with_events` 自动让新工具获得 tool_call/tool_result 事件

**新增内容**：

| 类型 | 说明 |
|---|---|
| 依赖 | `requirements.txt` 新增 `html2text~=2024.2.26` |
| 工具 | `backend/app/tools/fetch_url_tool.py` — `FetchUrlTool`（tool_key=`fetch_url`），requests+html2text 抓取 URL→markdown，超 20000 字截断 |
| 工具 | `backend/app/tools/kb_ingest_tool.py` — `KbIngestTool`（tool_key=`kb_ingest`），同步 psycopg2 engine + 同步 DashScope embedding 批量调用，切块入库到 document_configs/document_chunks |
| 注册 | `tools/__init__.py` + `crews/tool_registry.py` 注册两个新 tool_key |
| Skill | `网页内容编排入库`（skill_key=`web_ingest_orchestrator`），明确编排主管的审批循环职责：抓取→撰写→审阅→不达标指出问题→修改→达标入库 |
| Agent | `web_orchestrator`（内容编排主管，manager，max_iter=20，挂 skill，不挂 tools） |
| Agent | `web_reader`（网页阅读员，挂 fetch_url） |
| Agent | `web_writer`（内容撰写员，挂 write_markdown，挂 skill，max_iter=8） |
| Agent | `kb_writer`（知识库写入员，挂 kb_ingest） |
| Crew | `web_ingest_crew`（hierarchical，manager=web_orchestrator，agents=[reader, writer, kb_writer]） |
| Tasks | 4 个 task（全部 `agent=None`，由 manager 动态分配）：`fetch_url_content` / `write_structured_markdown` / `review_and_approve` / `ingest_to_kb` |

**审批循环设计**：CrewAI hierarchical 模式下，manager 自主决定由谁执行 task 并审阅产出。`review_and_approve` task 的 description 显式说明"由编排主管审阅"，引导 manager 在该步执行审批；若不达标，manager 应重新分派撰写员（step_callback 出现多轮 web_writer 思考）。manager 的 max_iter=20 允许循环多轮。

**入库工具同步实现**：
- `_get_sync_session()`：延迟初始化 psycopg2 engine（参考 rag_search_tool）
- `_embed_texts_sync(texts)`：同步批量调 DashScope `/v1/embeddings`，单批 25 条
- SQL：`INSERT INTO document_configs ... RETURNING id` + `INSERT INTO document_chunks ... CAST(:emb AS vector)`（与 rag_search_tool 同步 SQL 模式一致）
- tsv 列是 GENERATED ALWAYS AS to_tsvector('chinese', content) STORED，插入时自动生成，无需手动填值

**不引入 HITL**：审批由主 agent 自主执行（agent-to-agent review），非人类审批，故不用 HumanApprovalTool。

#### Week 10 关键设计决策

1. **完全复用 hierarchical 编排机制**：不改 `factory.py`，新增的 crew/agents/tasks/skills 通过 DB 配置自动被 `build_crew_from_db` 装配
2. **fetch_url 用 requests+html2text 而非 Playwright**：静态页面更轻量，避免启动 Chromium 的开销；对 JS 渲染页面后续可扩展降级到 Playwright
3. **kb_ingest 同步实现**：CrewAI akickoff() 在主事件循环调用工具 _run，不能用 asyncio.run。参考 rag_search_tool 完全同步路径，psycopg2 engine + 同步 requests embedding
4. **切块逻辑复用**：`_split_chunks` 是纯函数，直接 import 复用，不重复实现
5. **批量 embedding 分批 25 条**：DashScope 单次最多 25 条输入，超出自动分批
6. **审批循环靠 task description 引导**：`review_and_approve` task 的 description 显式说明"由编排主管执行"，manager 的 max_iter=20 允许多轮重新分派
7. **manager 不挂 tools**：遵循 CrewAI hierarchical 限制（manager 仅拆解委派）
8. **web_writer 挂 skill**：让撰写员理解入库标准，产出更易审批通过
9. **source_type 默认 'web'**：区别于 'text'（手动上传）和 'file'（文件上传），便于后续按来源过滤
10. **不新增 Alembic 迁移**：无新表，复用 document_configs/document_chunks

### Week 8 关键设计决策

1. **embedder 用 OpenAI provider 指向 DashScope**：CrewAI 的 `embedder` 字段接受 ProviderSpec dict，`provider="openai"` + `api_base` 可指向 DashScope 的 OpenAI 兼容端点，无需编写自定义 embedder，复用现有 `QWEN_API_KEY`
2. **LongTermMemory 用 SQLite 而非 pgvector**：进度文档原计划"long-term 用 pgvector"，但 CrewAI 1.9.3 的 LongTermMemory 实际用 `LTMSQLiteStorage`（SQLite 存任务质量评分），不需要额外基建；ShortTermMemory/EntityMemory 用 ChromaDB（RAGStorage），由 `embedder` config 指定 DashScope
3. **多轮对话用 Redis 而非 CrewAI 短期记忆**：当前架构每请求新建 Crew → CrewAI ShortTermMemory 不跨请求。用 Redis List 存对话历史，注入 Task description 前缀，实现跨请求短期记忆。CrewAI 内置记忆负责同一 kickoff 内的步骤间记忆 + 长期 SQLite 持久化
4. **session_id 前端生成**：`useChat` 用 `useRef` 持有 uuid，`newChat()` 重新生成，`streamChat` 随请求发送，后端通过 Redis 按 session_id 分组
5. **manager 决策视觉区分**：`step.agent === "团队主管"` 时渲染 Crown 图标 + 加粗边框 + 高亮背景，与 sub-agent 的 Search/Wrench 图标 + 普通背景形成对比
6. **retry 不重建 session**：重试保持同一 session_id，避免对话历史断裂；`newChat` 才生成新 session

## 三、技术债与已知问题

1. **AliyunLLM 非流式 API**：当前 `call()` 是阻塞返回完整响应，无 token 级流式。未来可修改 `aliyun_llm.py` 使用 `stream=True` 实现真流式
2. **CrewAI GBK 编码问题**：CrewAI 内部事件总线在 Windows GBK 控制台输出 emoji 时报错。Docker 容器内（UTF-8）无此问题，本地运行需设 `PYTHONUTF8=1`
